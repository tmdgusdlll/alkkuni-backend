# PLANNING.md

알꾼이에서 **무엇을 만들고, 왜 그렇게 정했는지**를 정리한 문서다.
자세한 근거는 노션 설계 문서와 스파이크 보고서에 있고, 여기에는 구현할 때 바로 필요한 결정만 둔다.

## 목표

- 식약처 공공데이터를 주기적으로 수집해, 원본을 보존한 채 제품·성분 데이터를 정규화한다.
- 성분별로 제품의 1일 섭취 기준 함량을 비교할 수 있는 검색 가능한 페이지를 제공한다.
- 서랍에 담은 제품이 회수되면 중복·누락 없이 이메일로 알린다.
- 모바일 우선 반응형, 서버 렌더링(SEO)으로 검색 유입을 만든다.
- AWS 비용 월 3만원 이하, 원본(S3)으로부터 DB 재구축 가능.

## 비목표

- 개인 맞춤 추천, 효능 평가·순위, 약물 상호작용 안내 (의료 조언 영역)
- 판매량 순위 (공개 데이터 없음)
- 네이티브 앱 (반응형 웹 → PWA → 앱 순서)
- 실시간 가격 비교 (크롤링 약관 리스크)
- 식약처 신고 정보가 없는 제품(해외 직구)의 함량 비교

| 서비스 | 용도 | 메모 |
|---|---|---|
| I0030 건강기능식품 품목제조 신고사항 | 제품 기본 정보, 함량(`STDR_STND`) | 약 4.6만 건. 페이징(1000건씩 47회) 또는 파일 방식(gzip CSV 1회) |

## 수집 파이프라인 (스파이크로 확인된 사실 기반)

- API 호출 한도: `CHNG_DT` 없이 호출하면 시간당 100회 (`INFO-320`). 식품안전나라 안내상 낮 시간에는 300회 제한도 있다(단위 미확인). 에러도 HTTP 200에 본문 `RESULT.CODE`로 온다.
- 한 번에 최대 1,000건. 1,000건 한 번에 약 4.2초(2026-11-02 실측, 스파이크 때는 타임아웃이 났었다).
- `CHNG_DT=YYYYMMDD`는 `LAST_UPDT_DTM` 기준으로 정확히 거른다. 신규 등록도 포함된다. 삭제 표현은 미확인.

| 작업 | 방식 | 주기 |
|---|---|---|
| 초기 적재 | 페이징으로 전체(1000건씩 47회, 약 3분)를 받고, 받은 신고번호 수가 `total_count`와 다르면 실패로 끝낸다. 멱등 upsert라 다시 돌리면 된다 | 최초 1회, 장애 복구 |
| 증분 수집 | `CHNG_DT=마지막 수집일 - 1일`, 멱등 upsert | 매일 |
| 전체 대사 | 파일 방식 `/api/{key}/I0030/file`(gzip CSV 약 15MB)로 한 시점 전체를 받아 해시 비교, 삭제·누락 보정. 페이징은 도중 변경으로 경계 행이 빠지면 "삭제"로 오판한다 | 주 1회 또는 월 1회 |
| 회수 수집 | I0490 전체(약 400건)를 받아 이전 스냅샷과 비교. 새 건은 저장·알림, 사라진 건은 삭제하지 않고 "목록에서 빠짐" 상태 | 매일(필요하면 하루 여러 번) |

- I0490은 식약처가 관리하는 "지금 유효한 회수 목록" 전체다(바뀐 것만 주는 기능 없음). 덜 받은 날에도 받은 건의 저장·갱신은 하고, "목록에 없음 → 빠짐" 판단만 다 받은 날에 한다.
- 지금 빠짐 판단은 "한 번에 절반 넘게 빠지면 건너뜀"만 막는다. 식약처가 `total_count`까지 줄여 일부만 보내면(예: 300건이던 목록이 하루 만에 200건) 오류일 가능성이 높지만, 절반 미만이라 그대로 `DELISTED`가 된다. 지금 고치지 않는 이유: `DELISTED`를 읽는 곳이 없고 다음 정상 수집 때 `LISTED`로 돌아오며, 기준을 정하려면 하루 실제 이탈 건수 데이터가 필요하다. `DELISTED`를 화면·알림 판단에 쓰기 시작하면 "N일 연속 목록에 없을 때만 `DELISTED`"로 바꾼다(N은 며칠 수집한 이탈 건수를 보고 정함).
- 원본은 S3에 수집 시각 기준 경로로 저장한다.
- 수집 커서(마지막 수집일)는 DB에 저장한다.
- `INFO-320`을 받으면 재시도하지 않고 멈춘다.
- 배치 작업은 `alkkuni.job=...`으로 켜면 한 번 실행하고 끝나는 컨테이너다(ADR-009). 매일 실행은 EC2 cron, 수동 실행은 관리자 버튼(아래 "관리자 운영 도구")으로 하고, 실행 잠금으로 겹치지 않게 한다.

## 성분 정규화

**규칙 → 실패분만 LLM → 확신도 낮은 값은 사람 검수.**

- 함량은 `STDR_STND`의 `성분명 : 표시량(숫자 단위/숫자 단위)의 80~150%` 형태에서 추출한다.
- 스파이크 결과: 추출률 80.8%, 무작위 200개 중 완전히 맞음 78.5%, 원문에 함량이 없는 제품 0.
- 파서 개선 목록 (영향 큰 순)
  1. 프로바이오틱스 균수 별도 규칙 (`1억`, `10^9`, `CFU/g`)
  2. 표시량 표기 변형 (`표시량[…]`, `｛…｝`, `표시량의(…)`, `(표시량 : 10mg / 500mg)`)
  3. "표시량" 단어 없는 형식 (`1.05mg/1,000mg의 80~180%`) → 단어가 아니라 함량 표기 모양으로 찾기
  4. 프로바이오틱스가 있으면 다른 성분까지 건너뛰는 버그를 반복하지 않기
  5. 단위가 성분명 괄호에 있는 형식 → LLM·검수 후보
  6. 분모가 단위만 있는 경우(`mg/g`)는 분모 1g
  7. 같은 제품 안에서 성분별 분모가 다르면 경고 (원문 오타 탐지)
- 분모는 대체로 1일 섭취량이지만 보장되지 않는다. 분모를 확인하지 못한 값은 "표시 기준량" 배지로 구분한다(아래 "검색·목록·비교 화면").
- 정규화 사전: 단위 표기 통일(㎍/μg/ug/µg), 영양소별 환산 단위(α-TE, NE, RAE, DFE) 규칙, 성분명 동의어(셀렌=셀레늄). DB 테이블로 관리한다(Elasticsearch 아님).
- 단위 변환은 성분별 규칙으로 한다. (비타민D 1μg = 40IU, 비타민A·E는 원료 형태에 따라 다름)
- B2B 원료 품목(섭취방법에 "원료로 사용")은 비교 대상에서 뺀다.

## 검색·목록·비교 화면 (2026-11-05 정함)

화면은 검색, 성분별 제품 목록, 제품 비교, 제품 상세다. 성분별 제품 목록과 제품 비교는 프론트에서 한 화면(`/explore`, 위 목록 + 아래 비교 칸)이고 API는 둘이다(2026-11-11, 프론트 `DESIGN.md` 8.2·8.3). 쿼리 빌더가 필요한 곳은 성분별 제품 목록뿐이다.

| 화면 | API(안) | 쿼리 |
|---|---|---|
| 검색 | `GET /api/products?q=&sort=` | 네이티브 SQL(pg_trgm). 조건이 고정이고 유사도 함수는 JPQL로 표현할 수 없다 |
| 성분별 제품 목록 | `GET /api/products/explore?ingredient=&exclude=&form=&min=&max=&sort=` (성분 고르기는 `GET /api/ingredients`) | Kotlin JDSL. 선택 조건이 많고 `EXISTS`·`NOT EXISTS`가 반복된다. 함량순은 ORDER BY 상관 서브쿼리 |
| 제품 비교 | `GET /api/products/compare?ids=` | 고정 쿼리(JPA) |

**검색**: 필터 없이 정렬만 둔다(관련도순, 최신 신고순, 성분 함량 높은순). 함량순은 검색어가 성분과 일치할 때만 켠다.

**성분별 제품 목록**
- 성분을 여러 개 고를 수 있고, 고른 성분이 **모두** 든 제품만 남는다(AND). 고른 성분마다 표에 함량 열이 생긴다.
- 정렬은 고른 성분 중 **하나**의 1일 함량 높은순이다. 기본값은 처음 고른 성분이고, 사용자가 다른 고른 성분이나 최신 신고순으로 바꾼다. API는 `sort=amount:{ingredientId}`를 받고, 그 성분이 고른 성분 목록에 있는지 검증한다.
- 여러 성분을 합친 점수(합계, 기준치 대비 % 평균)로는 정렬하지 않는다. 단위가 달라 합할 수 없고, % 평균은 한 성분을 과하게 넣은 제품을 위로 올리는 순위가 된다(비목표 "효능 평가·순위"). "모두 충분히 든 제품"은 정렬이 아니라 "1일 기준 충족" 필터로 찾는다.
- 1일 함량을 모르는 제품은 목록 맨 뒤에 "함량 확인 불가"로 둔다.
- 필터와 데이터 상태

| 필터 | 데이터 | 할 일 |
|---|---|---|
| 성분 포함(모두) | `product_ingredient.ingredient_id` | 없음 |
| 제외 성분 | 같음 | 없음 |
| 성분 함량 범위 | `daily_amount` | 기준 성분(`sort=amount:{id}`, 없으면 첫 성분) 하나에만, 주 단위 값에만 건다 (구현, 2026-11-08) |
| 하루 섭취량 | `intake_times_per_day`, `intake_units_per_time` | 구간(하루 1번, 1회 1개) 정하기 |
| 단일/복합 원료 | I0030 `INDIV_RAWMTRL_NM`(기능성 원료 목록) | 수집함(`product.functional_materials`). 단일/복합 판정 규칙 |
| 제형 | I0030 `PRDT_SHAP_CD_NM`(정·캡슐·분말·액상 등 코드값 14종) | 수집함(`product.form`) |
| 브랜드 | I0030에 없음. `BSSH_NM`은 위탁생산 제조사다(예: "여에스더" 제품의 제조사가 10곳 넘음) | 브랜드 사전 |
| 기능성(눈·간·혈당·체지방 등) | I0030 `PRIMARY_FNCLTY`는 자유 문장이라 키워드로 거르면 틀린다("간"이 "간혹"에 걸림) | 수집 + 기능성 카테고리 사전 |
| 1일 기준 충족 | 기준값 없음 | 성분별 기준값 |
| 회수 제품 제외 | `recall` 매칭 전 | 회수 매칭 뒤 |

**제품 비교**: 2~3개를 담아 성분을 행, 제품을 열로 놓는다. 성분마다 기준 대비 %와 충족·미달을 표시하고, 가장 많은 값을 강조한다. 없는 성분은 "-". 목록·제품 검색에서 "추가"로 하나씩 담고 빼며, 3개가 찬 뒤 더 담으려 하면 "3개까지만 비교할 수 있어요"를 보여준다. 1개만 담았을 때는 API를 부르지 않는다(2026-11-11).

**함량 표시 규칙**
- 분모를 확인한 값은 "1일 기준", 분모를 확인하지 못한 값(`basis_check`가 `UNVERIFIED`·`UNREADABLE`)은 "표시 기준량" 배지를 단다(디자인 초안, 2026-11-06). 값은 성분표 기준량당 함량 그대로라 "추정"보다 사실에 가깝다. 로컬 기준 원료 제외 제품의 77%다. 이 비율을 줄이는 일은 따로 시간을 들여 개선한다.
- 1일 함량을 모르는 행(원료 제외 성분 행의 약 1.2%, `/g` 분모에 중량 없음·환산 규칙 없는 단위)은 숨기지 않는다. 막대·기준치 % 없이 성분표 원문 값을 보여주고 함량순 정렬에서 맨 뒤에 둔다. 함량 범위 필터에서는 빠진다.
- 한 성분 안에 단위가 섞인 성분(엽산 DFE·mg, 비타민 A RAE·RE·mg, 나이아신 NE·mg, 비타민 E α-TE·mg)은 원료(합성/천연 등)를 몰라 환산하지 않는다. 주 단위(`ingredient.default_unit`)를 정해 함량순은 주 단위 값 → 다른 단위 값 → 모르는 값 순, 함량 범위는 주 단위 값에만 건다. 화면은 단위가 주 단위와 다르면 "다른 단위 표기"로 구분한다(2026-11-08).
- 1일 기준: 비타민·무기질은 **영양성분 기준치 100% 이상**, 기능성 원료는 **고시 1일 섭취량 최소값 이상**이면 충족이다. 성분별 기준값·상한은 `ingredient`에 칼럼으로 두고, 출처는 `docs/daily-reference.csv`에 남긴다. "상한 초과" 배지는 달지 않는다(2026-11-06). 대신 1일 함량이 상한의 2배를 넘으면 오류로 의심해 "검수 대기" 경고를 단다. 저장하지 않고 응답 때 계산한다(2026-11-09). 상한은 비타민·무기질은 상한섭취량, 기능성 원료는 고시 1일 섭취량 최고값이다(일부 제외, `docs/daily-reference.csv`).
- 같은 제품에 같은 성분 행이 여러 개면(로컬 505쌍, 217개 제품) **합치지 않고 모두 보여준다**("5.95mg + 2.55mg"). 원문 표본 조사(2026-11-07) 결과 원인이 섞여 규칙 하나로 맞출 수 없다.
  - 약 72%(361쌍)는 멀티팩의 구성품별 성분표다. 합산이 맞다. 값이 완전히 같은 쌍(116쌍)도 88쌍이 멀티팩이라 "같은 값 = 중복"도 아니다.
  - 나머지는 같은 내용의 중복 기재다. 수출국별 규격(`[말레이시아]`·`<영국>`), 원료용/최종제품용 규격, 유산균 합계와 일부(`프로바이오틱스 수`·`유산균 수`), 1정 기준과 1포 기준. 하나만 맞고 합산하면 부풀려진다.
  - 어느 구성품·국가의 값인지 지금 데이터에 없어 자동으로 가를 수 없다. 정확히 합치려면 파서가 구간을 나눠 `product_ingredient`에 칼럼을 둬야 한다(파서 버전 업 + 재적재). 영향이 제품의 0.5%라 관리자 검수 뒤로 미룬다.
  - 검색 함량순은 가장 큰 값 하나로 정렬한다(멀티팩은 실제보다 낮게 정렬된다). 비교의 "가장 많은 값 강조"는 제품마다 행이 하나이고 단위가 같은 성분에만 한다.

**브랜드 사전**: 사용자는 제조사보다 브랜드로 찾고 비교한다. 성분 사전과 같은 방식으로, 제품명에서 브랜드 후보를 뽑아 CSV로 검토한 뒤 Flyway로 넣는다. 이름에 브랜드가 없는 제품(예: "눈에는 눈 NOON")이 있어 연결률을 실측한다. 같은 이름 제품이 신고번호만 다르게 여러 개 있는 경우(예: "비타민C 4000 영국산" 3건) 목록에서 묶을지도 이때 정한다.

정함(2026-11-12, V13):
- 식약처 공개 데이터(I0030, C003, 생산실적, 판매업 인허가)에는 제품별 판매사(유통전문판매원) 칸이 없다. 브랜드는 제품명에서만 뽑는다.
- 범위는 "제품명에 보이는 브랜드"다. 제품명이 표기로 시작하면 연결하고(가장 긴 표기 우선), 이름 중간은 보지 않는다. 회사가 브랜드로 내세우는 라인(락토핏, 듀오락, 화애락 등)도 독립 브랜드로 둔다.
- 검토(`docs/brand-dictionary.csv`, 근거 URL 포함)에서 접두어 일괄 연결이 위험한 표기는 보류했다(한미, 안국, 동국, 유한M 등). 보류 표기는 `brand_id` NULL로 사전에 남겨, 더 짧은 표기로 잘못 연결되지 않게 한다("유한M …"이 "유한" → 유한양행으로 가지 않음).
- 운영사(여에스더·닥터에스더 → 에스더포뮬러)와 제품별 수동 지정은 두지 않는다. 운영사는 쓸 화면이 생기면 `brand`에 칸을 더하고, 제품별 지정은 관리자 검수(4단계)에서 한다.
- 연결률은 로컬 원료 제외 제품 43,449개 중 5,326개(12.3%)다. 화면은 브랜드 없는 제품을 기본으로 둔다.
- API(2026-11-12): 제품 응답의 `brand`(`{id, name}`, 없으면 null), 검색어가 브랜드 표기와 정확히 맞으면 그 브랜드 제품을 더하고 `matchedBrand`로 알린다, 성분별 목록 `brand=`(OR), 브랜드 목록 `GET /api/brands`(공개 제품이 있는 브랜드, 제품 수 순).
- 같은 이름 제품은 묶지 않는다. 이름이 겹치는 6,501개(2,647종)의 대부분이 "밀크씨슬"(29개, 제조사 28곳)처럼 다른 회사의 일반 이름이다.

## 인증

- Spring Security OAuth2 Client, 카카오·네이버·구글. 제공자를 추상화해 추가가 쉽게 한다.
- 이메일은 회수 알림에 필요하다. 이메일이 없거나 동의하지 않은 경우 로그인 후 입력받는 화면을 둔다.
- 여러 제공자로 가입한 같은 사람의 계정은 MVP에서 자동 병합하지 않는다.
- 카카오 연결 해제 웹훅·네이버 연결끊기 알림을 받으면 해당 소셜 계정과 회원 정보를 삭제한다(멱등). 공개 HTTPS 주소가 필요하므로 배포 후 등록.
- 인앱 브라우저에서 구글 로그인이 막힐 수 있다. 대응 방식은 미해결.
- 로그인 상태는 세션으로 유지한다(JWT 안 씀, 2026-11-07). OAuth2는 콜백에서 한 번 본인을 확인할 뿐이고, 그 뒤 요청은 Spring Security 세션 쿠키로 알아본다.
  - 저장소는 `spring-session-jdbc`(Postgres). 기본값(api 메모리)이면 배포·재시작 때 모든 사용자가 로그아웃된다. 서버가 늘어도 공유 저장소라 그대로 쓴다.
  - JWT를 안 쓰는 이유: 연결 해제 웹훅·탈퇴·관리자 권한 회수 때 즉시 무효화해야 한다. JWT는 만료 전까지 취소가 어렵고, 차단 목록을 두면 결국 저장소 조회라 세션과 같다.
  - Redis를 캐시로 도입하면 세션 저장소도 `spring-session-data-redis`로 옮길 수 있다(로그인 코드는 그대로).
  - 쿠키 기반이라 CSRF 보호를 켠다. CloudFront가 `/api/*`에 쿠키를 넘기도록 설정한다.

## 구매 링크

- 자체 API가 링크를 내려준다(링크 정책 변경, 클릭 로그, 키 보호).
- MVP는 수동 등록 링크. 쿠팡 파트너스 API는 최종 승인(누적 판매 15만원 초과) 후.
- 구매 버튼 근처에 대가성 문구를 표시하고, 수수료가 순위·노출에 영향을 주지 않는다.

## 관리자 운영 도구 (MVP 다음)

자동 판정으로 끝나지 않는 데이터가 실제로 쌓인다(초기 적재 기준 `NEEDS_REVIEW` 300, `NO_AMOUNT` 1,062, 번호로 매칭되지 않는 회수 약 56%). 이걸 DB를 직접 고치지 않고 처리할 화면과 API를 만든다. 사용자는 운영자 본인뿐이다.

- 파싱 검수 대기열: `NEEDS_REVIEW`·`NO_AMOUNT` 제품을 원문 `STDR_STND`와 파싱 결과를 나란히 보고 고친 뒤 `REVIEWED`로 바꾼다. 재수집이 `REVIEWED`를 덮지 않는 건 `Product.applyParse`가 이미 지킨다.
- 회수 매칭 검수: `RecallMatchCandidate` 수락·거절.
- 수집 현황: 출처별 커서, 마지막 실행 시각·건수·실패 여부, 수동 실행 버튼.
- 수동 실행 방식: API는 `collect_request`에 `PENDING` 한 줄만 쓴다. EC2 cron이 1분마다 `PENDING`을 확인해 `RUNNING`으로 바꾸고 batch 컨테이너를 띄우며, batch가 끝나면 `DONE`/`FAILED`와 건수를 남긴다. 새벽 정기 수집도 cron이 같은 테이블에 요청을 넣어 같은 경로로 돈다. API에 Docker 소켓이나 AWS 권한을 주지 않으려는 것이고, 요청 행이 그대로 수집 이력이 된다. 버튼 후 시작까지 최대 1분 걸린다.
- 권한: `Member.role`(`USER`/`ADMIN`). `/admin/**`은 `ADMIN`만, 서비스 메서드에도 `@PreAuthorize`. 관리자는 소셜 로그인 + 허용 목록이 주된 보호이고, Nginx `/admin` IP 제한은 보조(집 IP가 바뀔 수 있음). 역할 세분화(검수 전용 등)는 운영자가 늘면 추가.
- 감사 로그: `admin_audit_log`에 누가·언제·무엇을·전후 값을 남긴다. 변경과 같은 트랜잭션에서 기록하고, 추가만 한다(수정·삭제 없음).
- 하지 않는 것: 별도 관리자 서버, 외부 인증 서버(Keycloak 등), 리소스별 권한 테이블, 자체 MFA(소셜 제공자의 2단계 인증으로 대신).

## 보안 운영

사고가 난 뒤에 고치는 것에 그치지 않도록, 아래 항목을 미리 넣어 두고 PR마다 같은 기준으로 점검한다.

- 실제 사용자 IP 복원: CloudFront 뒤라 Nginx가 보는 연결 IP는 모두 CloudFront다. `set_real_ip_from`(CloudFront 대역) + `real_ip_header X-Forwarded-For`로 CloudFront가 보낸 헤더만 믿는다. 이게 없으면 아래 호출 제한과 IP 제한이 CloudFront 단위로 걸린다.
- 직접 접속 차단: EC2 보안 그룹의 80/443은 CloudFront 관리형 prefix list만 허용한다. EC2 IP로 바로 와서 헤더를 꾸미는 요청을 막는다.
- 공개 API 호출 제한: Nginx `limit_req`.
- 소셜 연결 해제 웹훅은 서명·출처 검증을 테스트로 남긴다.
- GitHub Dependabot·secret scanning을 켠다.
- `REVIEW.md`에 보안 체크리스트를 두고, 위험 경로 PR은 `/security-review` 결과를 PR에 남긴다.
- 회원 탈퇴 시 개인정보 삭제를 테스트로 증명한다.

## 배포

- 프론트·백엔드 레포와 CI/CD 분리. 이미지 태그는 커밋 해시, EC2 `.env`의 `WEB_TAG`/`API_TAG`로 관리.
- 운영 compose와 `nginx.conf`는 백엔드 레포 `deploy/`에 둔다(2026-11-09 정함). api·batch·db·nginx가 이 레포에 있고, web은 `WEB_TAG` 이미지로만 들어온다. 프론트 CI는 태그를 바꾸고 `docker compose pull web && docker compose up -d --no-deps web`만 한다. 별도 infra 레포는 지금 규모에 과하다.
- Nginx 라우팅: `/api/*`·`/actuator/health`는 api 컨테이너로, 나머지(`/`)는 web(Next.js) 컨테이너로 넘긴다.
- 기본 배포 범위(2026-11-09 정함): Nginx(위 라우팅만) + api + batch + db. web이 아직 없어서 `/`는 502가 나도 된다. 보안 그룹 80·443은 닫아 두고, 헬스 체크는 SSM으로 EC2 안에서 Nginx를 거쳐(`curl localhost/actuator/health`) 한다. batch는 초기 적재와 메모리 실측(batch 실행 중 `docker stats`·swap 피크) 때문에 함께 올린다.
  - CloudFront를 붙일 때 한꺼번에 넣는 것: `set_real_ip_from`·`real_ip_header`, `limit_req`, `/admin` IP 제한, 보안 그룹을 CloudFront prefix list로 열기. CloudFront를 거친 요청이 있어야 제대로 걸리는지 확인할 수 있어서 미룬다.
- 배포는 서비스 단위 교체(`docker compose pull api && docker compose up -d --no-deps api`). `docker compose down`은 배포에 쓰지 않는다.
- CI/CD 단계: (1) 테스트·빌드·ECR 푸시 → (2) SSM으로 교체 → (3) 헬스 체크(`/actuator/health`) 실패 시 직전 태그로 자동 롤백.
- 컨테이너별 `mem_limit`, JVM 힙 크기 조정. 2GB가 부족하면 t4g.medium 검토.
- 인스턴스(2026-11-07 정함): t4g.small로 시작하고 기본 배포 때 메모리를 실측한다. 부족하면 중지 → 인스턴스 유형 변경 → 시작으로 medium에 올린다(EBS 데이터 유지, 같은 t4g(ARM) 안에서만). medium은 월 약 5만원으로 ADR-004 예산(월 3만원)을 넘으니 올릴 때 ADR-004를 고친다.
  - 처음부터 탄력적 IP를 붙인다. 중지·시작하면 일반 공인 IP가 바뀌어 CloudFront 원본이 끊긴다.
  - swap 파일 1~2GB를 안전망으로 둔다(`swappiness` 낮게). batch가 도는 동안 OOM killer가 Postgres·api를 죽이는 것을 막는 용도다. swap을 꾸준히 쓰면 증설 신호다. 컨테이너 `mem_limit`은 swap과 별개로 넘으면 죽는다.
  - RDS는 지금 쓰지 않는다. 같은 돈이면 medium이 메모리를 더 준다. 서버 2대 이상, 하루치 데이터 손실 불가, Multi-AZ가 필요해지면 DB부터 RDS로 뺀다.
- 백업(2026-11-07 정함): 매일 cron으로 `pg_dump` → S3, 수명 주기로 30일 안팎 보관. 제품·성분은 식약처에서 다시 받을 수 있지만 회원·서랍·알림 내역·검수 결과·감사 로그는 되살릴 수 없다. 복구 훈련: 빈 Postgres 컨테이너에 복원하고 행 수를 원본과 대조, 걸린 시간을 기록한다. 시점 복구는 안 된다(최대 하루치 손실).

## 캐시

순서(2026-11-07 정함): 브라우저 캐시 → CloudFront 캐시 → Redis. 앞 단계가 싸고, 뒤로 갈수록 메모리·운영 부담이 든다.

- 공개 조회 API(검색·비교·상세·성분별 목록): 성공 응답에 `Cache-Control: public, max-age=60`. 식약처 데이터는 하루 한 번 바뀌어 60초 지연은 문제없다. 같은 사용자의 뒤로 가기·재방문이 빨라진다(여러 사용자 사이 부하는 못 줄인다).
- CloudFront를 붙일 때 `s-maxage=60`과 공개 조회 경로의 캐시 정책을 켠다. 여러 사용자의 같은 요청을 CloudFront가 대신 답한다.
- 회원마다 다른 응답(서랍, 마이페이지, "서랍에 담김" 표시가 섞인 응답)은 `no-store` 또는 `private`. `public`으로 CloudFront에 캐시되면 남의 응답이 보인다. 서랍 여부는 별도 API로 나눈다.
- 에러 응답(404·500)은 캐시하지 않는다.
- Spring Security는 기본으로 모든 응답에 `no-cache, no-store`를 붙인다. 인증을 넣을 때 공개 조회 API의 헤더가 덮이지 않는지 테스트로 막는다.
- Next.js 정적 파일(해시가 붙은 JS·CSS·아이콘)은 Next.js 기본값(1년, `immutable`).
- Redis는 위로도 느린 쿼리가 남을 때(`EXPLAIN ANALYZE`로 확인) 캐시로 들인다. 메모리를 쓰므로 small 메모리 실측 뒤.

## 메인 인기 성분 (2026-11-12 정함)

1. 지금(MVP): 프론트 메인(`/`)이 고정 성분 6개를 띄운다. 성분은 연결된 제품 수가 많은 순서(로컬 2026-11-12: 아연 12,349, 비타민 D 9,778, B6 8,413, B1 8,054, B2 7,617, C 7,344)이고 모두 기준치가 있다. API는 새로 만들지 않고 프론트가 기존 성분별 목록 API(`size=3`, 성분 함량순)를 성분마다 부른다. 성분 목록은 프론트 상수다. 랜덤으로 띄우지 않는다(사전 대부분이 낯선 성분이고, 매번 바뀌면 캐시를 못 쓴다).
2. 다음(백엔드): 조회 기반 인기 순위를 만들고 성능을 잰다.
   - 날짜별 카운트 테이블 `(view_date, ingredient_id, count)`, PK `(view_date, ingredient_id)`. 볼 때마다 `INSERT ... ON CONFLICT DO UPDATE SET count = count + 1`. 행 수가 "날짜 × 성분 수"로 묶여(1년 215 × 365 ≈ 8만) 오래된 기록을 지우지 않아도 되고, "최근 7일"도 셀 수 있다. 볼 때마다 한 줄씩 쌓기(기간은 자유롭지만 계속 커짐)와 성분별 누적 숫자 하나(예전 인기가 위에 남음)는 쓰지 않는다.
   - 순위는 하루 한 번 배치(`alkkuni.job=...` + cron)로 최근 7일을 합쳐 작은 순위 테이블에 저장하고, `GET /api/home/popular`(이름은 안)는 그 테이블만 읽는다. 기록이 없거나 모자라면 1의 고정 목록을 돌려준다.
   - 조회 기록은 성분별 목록 API 안에서 세지 않는다. 프론트 서버 캐시(`"use cache"`), 응답 `max-age=60`, CloudFront가 앞에서 답해 백엔드가 조회를 거의 못 본다. 브라우저가 따로 보내는 기록 요청(예: `POST /api/views`, 캐시 안 함)이 필요하고, 무엇을 셀지(목록에서 고른 성분, 검색어에 잡힌 성분, 상세에서 본 제품의 성분)와 새로고침 반복·봇 거르기는 이 작업 때 정한다.
   - 성능: k6로 같은 날 같은 성분에 기록 요청을 몰아 카운트 `UPDATE`의 행 잠금 대기와 응답 시간을 재고 노션 "성능 개선"에 남긴다.
3. 결과를 보고 정한다.
   - DB로 충분하면 그대로, 잠금 대기가 응답에 보이거나 실시간 순위가 필요하면 Redis Sorted Set(`ZINCRBY popular:ingredients:{날짜}`, 날짜 키 TTL, 최근 7일은 `ZUNIONSTORE`)으로 카운트만 옮긴다. 하루치 순위는 계속 DB에 남긴다. 캐시용 Redis(위 "캐시")가 이미 들어와 있으면 인프라 부담이 없어 옮기기 쉽다. 어느 쪽이든 `GET /api/home/popular` 응답은 같아 프론트는 영향이 없다.
   - 프론트는 배포 뒤 실제 기록이 쌓이면 고정 목록 대신 `GET /api/home/popular`에서 성분 목록을 받는다(카드 코드는 그대로). 그 전에는 API도 고정 목록을 돌려주므로 바꿀 이유가 없다.
