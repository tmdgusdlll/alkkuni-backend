# PLANNING.md

알꾼이에서 **무엇을 만들고, 왜 그렇게 정했는지**를 정리한 문서다.
자세한 근거는 노션 설계 문서와 스파이크 보고서에 있고, 여기에는 구현할 때 바로 필요한 결정만 둔다.

## 목표

- 식약처 공공데이터를 주기적으로 수집해, 원본을 보존한 채 제품·성분 데이터를 정규화한다.
- 성분별로 제품의 1일 섭취 기준 함량을 비교할 수 있는 검색 가능한 페이지를 제공한다.
- 서랍에 담은 제품이 회수되면 중복·누락 없이 이메일로 알린다.
- 모바일 우선 반응형, 서버 렌더링(SEO)으로 검색 유입을 만든다.
- AWS 비용 월 3만원 이하, 원본(S3)으로부터 DB 재구축 가능.

## 비목표

- 개인 맞춤 추천, 효능 평가·순위, 약물 상호작용 안내 (의료 조언 영역)
- 판매량 순위 (공개 데이터 없음)
- 네이티브 앱 (반응형 웹 → PWA → 앱 순서)
- 실시간 가격 비교 (크롤링 약관 리스크)
- 식약처 신고 정보가 없는 제품(해외 직구)의 함량 비교

## 수집 파이프라인 (스파이크로 확인된 사실 기반)

- API 호출 한도: `CHNG_DT` 없이 호출하면 시간당 100회 (`INFO-320`). 식품안전나라 안내상 낮 시간에는 300회 제한도 있다(단위 미확인). 에러도 HTTP 200에 본문 `RESULT.CODE`로 온다.
- 한 번에 최대 1,000건. 1,000건 한 번에 약 4.2초(2026-11-02 실측, 스파이크 때는 타임아웃이 났었다).
- `CHNG_DT=YYYYMMDD`는 `LAST_UPDT_DTM` 기준으로 정확히 거른다. 신규 등록도 포함된다. 삭제 표현은 미확인.

| 작업 | 방식 | 주기 |
|---|---|---|
| 초기 적재 | 페이징으로 전체(1000건씩 47회, 약 3분)를 받고, 받은 신고번호 수가 `total_count`와 다르면 실패로 끝낸다. 멱등 upsert라 다시 돌리면 된다 | 최초 1회, 장애 복구 |
| 증분 수집 | `CHNG_DT=마지막 수집일 - 1일`, 멱등 upsert | 매일 |
| 전체 대사 | 파일 방식 `/api/{key}/I0030/file`(gzip CSV 약 15MB)로 한 시점 전체를 받아 해시 비교, 삭제·누락 보정. 페이징은 도중 변경으로 경계 행이 빠지면 "삭제"로 오판한다 | 주 1회 또는 월 1회 |
| 회수 수집 | I0490 전체(약 400건)를 받아 이전 스냅샷과 비교. 새 건은 저장·알림, 사라진 건은 삭제하지 않고 "목록에서 빠짐" 상태 | 매일(필요하면 하루 여러 번) |

- I0490은 식약처가 관리하는 "지금 유효한 회수 목록" 전체다(바뀐 것만 주는 기능 없음). 덜 받은 날에도 받은 건의 저장·갱신은 하고, "목록에 없음 → 빠짐" 판단만 다 받은 날에 한다.
- 지금 빠짐 판단은 "한 번에 절반 넘게 빠지면 건너뜀"만 막는다. 식약처가 `total_count`까지 줄여 일부만 보내면(예: 300건이던 목록이 하루 만에 200건) 오류일 가능성이 높지만, 절반 미만이라 그대로 `DELISTED`가 된다. 지금 고치지 않는 이유: `DELISTED`를 읽는 곳이 없고 다음 정상 수집 때 `LISTED`로 돌아오며, 기준을 정하려면 하루 실제 이탈 건수 데이터가 필요하다. `DELISTED`를 화면·알림 판단에 쓰기 시작하면 "N일 연속 목록에 없을 때만 `DELISTED`"로 바꾼다(N은 며칠 수집한 이탈 건수를 보고 정함).
- 원본은 S3에 수집 시각 기준 경로로 저장한다.
- 수집 커서(마지막 수집일)는 DB에 저장한다.
- `INFO-320`을 받으면 재시도하지 않고 멈춘다.
- 배치 작업은 `alkkuni.job=...`으로 켜면 한 번 실행하고 끝나는 컨테이너다(ADR-009). 매일 실행은 EC2 cron, 수동 실행은 관리자 버튼(아래 "관리자 운영 도구")으로 하고, 실행 잠금으로 겹치지 않게 한다.

## 성분 정규화

**규칙 → 실패분만 LLM → 확신도 낮은 값은 사람 검수.**

- 함량은 `STDR_STND`의 `성분명 : 표시량(숫자 단위/숫자 단위)의 80~150%` 형태에서 추출한다.
- 스파이크 결과: 추출률 80.8%, 무작위 200개 중 완전히 맞음 78.5%, 원문에 함량이 없는 제품 0.
- 파서 개선 목록 (영향 큰 순)
  1. 프로바이오틱스 균수 별도 규칙 (`1억`, `10^9`, `CFU/g`)
  2. 표시량 표기 변형 (`표시량[…]`, `｛…｝`, `표시량의(…)`, `(표시량 : 10mg / 500mg)`)
  3. "표시량" 단어 없는 형식 (`1.05mg/1,000mg의 80~180%`) → 단어가 아니라 함량 표기 모양으로 찾기
  4. 프로바이오틱스가 있으면 다른 성분까지 건너뛰는 버그를 반복하지 않기
  5. 단위가 성분명 괄호에 있는 형식 → LLM·검수 후보
  6. 분모가 단위만 있는 경우(`mg/g`)는 분모 1g
  7. 같은 제품 안에서 성분별 분모가 다르면 경고 (원문 오타 탐지)
- 분모는 대체로 1일 섭취량이지만 보장되지 않는다. 분모를 확인하지 못한 값은 "표시 기준량" 배지로 구분한다(아래 "검색·목록·비교 화면").
- 정규화 사전: 단위 표기 통일(㎍/μg/ug/µg), 영양소별 환산 단위(α-TE, NE, RAE, DFE) 규칙, 성분명 동의어(셀렌=셀레늄). DB 테이블로 관리한다(Elasticsearch 아님).
- 단위 변환은 성분별 규칙으로 한다. (비타민D 1μg = 40IU, 비타민A·E는 원료 형태에 따라 다름)
- B2B 원료 품목(섭취방법에 "원료로 사용")은 비교 대상에서 뺀다.

## 검색·목록·비교 화면 (2026-11-05 정함)

화면은 검색, 성분별 제품 목록, 제품 비교, 제품 상세다. 성분별 제품 목록과 제품 비교는 프론트에서 한 화면(`/explore`, 위 목록 + 아래 비교 칸)이고 API는 둘이다(2026-11-11, 프론트 `DESIGN.md` 8.2·8.3). 쿼리 빌더가 필요한 곳은 성분별 제품 목록뿐이다.

| 화면 | API(안) | 쿼리 |
|---|---|---|
| 검색 | `GET /api/products?q=&sort=` | 네이티브 SQL(pg_trgm). 조건이 고정이고 유사도 함수는 JPQL로 표현할 수 없다 |
| 성분별 제품 목록 | `GET /api/products/explore?ingredient=&category=&exclude=&form=&min=&max=&sort=` (성분 고르기는 `GET /api/ingredients`, 카테고리는 `GET /api/categories`) | Kotlin JDSL. 선택 조건이 많고 `EXISTS`·`NOT EXISTS`가 반복된다. 함량순은 ORDER BY 상관 서브쿼리 |
| 제품 비교 | `GET /api/products/compare?ids=` | 고정 쿼리(JPA) |

**검색**: 필터 없이 정렬만 둔다(관련도순, 최신 신고순, 성분 함량 높은순). 함량순은 검색어가 성분과 일치할 때만 켠다.

**성분별 제품 목록**
- 성분을 여러 개 고를 수 있고, 고른 성분이 **모두** 든 제품만 남는다(AND). 고른 성분마다 표에 함량 열이 생긴다.
- 정렬은 고른 성분 중 **하나**의 1일 함량 높은순이다. 기본값은 처음 고른 성분이고, 사용자가 다른 고른 성분이나 최신 신고순으로 바꾼다. API는 `sort=amount:{ingredientId}`를 받고, 그 성분이 고른 성분 목록에 있는지 검증한다.
- 여러 성분을 합친 점수(합계, 기준치 대비 % 평균)로는 정렬하지 않는다. 단위가 달라 합할 수 없고, % 평균은 한 성분을 과하게 넣은 제품을 위로 올리는 순위가 된다(비목표 "효능 평가·순위"). "모두 충분히 든 제품"은 정렬이 아니라 "1일 기준 충족" 필터로 찾는다.
- 1일 함량을 모르는 제품은 목록 맨 뒤에 "함량 확인 불가"로 둔다.
- 필터와 데이터 상태

| 필터 | 데이터 | 할 일 |
|---|---|---|
| 성분 포함(모두) | `product_ingredient.ingredient_id` | 없음 |
| 제외 성분 | 같음 | 없음 |
| 성분 함량 범위 | `daily_amount` | 기준 성분(`sort=amount:{id}`, 없으면 첫 성분) 하나에만, 주 단위 값에만 건다 (구현, 2026-11-08) |
| 하루 섭취량 | `intake_times_per_day`, `intake_units_per_time` | 구간(하루 1번, 1회 1개) 정하기 |
| 단일/복합 원료 | I0030 `INDIV_RAWMTRL_NM`(기능성 원료 목록) | 수집함(`product.functional_materials`). 단일/복합 판정 규칙 |
| 제형 | I0030 `PRDT_SHAP_CD_NM`(정·캡슐·분말·액상 등 코드값 14종) | 수집함(`product.form`) |
| 브랜드 | I0030에 없음. `BSSH_NM`은 위탁생산 제조사다(예: "여에스더" 제품의 제조사가 10곳 넘음) | 브랜드 사전 |
| 기능성(눈·간·혈당·체지방 등) | I0030 `PRIMARY_FNCLTY`는 자유 문장이라 키워드로 거르면 틀린다("간"이 "간혹"에 걸림) | 수집함. 판정은 고시 문구 단위 어간 규칙(`FunctionalCategory`, 24개, 영양소 기능 문구 제외), 저장은 `product_category`(V15, 2026-11-13). 필터 `category=`(하나만)·카테고리 목록 API(`GET /api/categories`) 구현(2026-11-13, 아래 "기능성으로 찾기") |
| 1일 기준 충족 | 기준값 없음 | 성분별 기준값 |
| 회수 제품 제외 | `recall` 매칭 전 | 회수 매칭 뒤 |

**기능성으로 찾기** (2026-11-13): 성분을 몰라도 "눈 건강" 같은 기능성으로 제품을 고르게 한다. 새 API 없이 성분별 제품 목록(`/explore`)이 성분 또는 카테고리 하나만 있어도 목록을 낸다.
- 카테고리는 하나만 고른다(입구 역할). 여러 개를 고르면 교집합·합집합을 정해야 하는데 쓰임이 없다. 검색 API에는 붙이지 않는다(검색은 정렬만).
- 성분 없이 카테고리만 고르면 기준 성분이 없어 함량순·함량 범위·기준 충족을 거절(400)하고 기본 정렬은 최신 신고순이다. 응답의 `ingredients`·`amounts`는 비고 `baseIngredientId`는 null이다. 대신 항목마다 기능성 원료 원문(`functionalMaterials`)과 `categories`를 붙여 어떤 원료 제품인지 보이게 한다. 성분을 하나 고르면 지금처럼 함량순 비교로 좁혀진다.
- 카테고리 목록은 `FunctionalCategory` 순서 24개 전부이고 제품이 없어도 0으로 낸다. 목록·비교·상세 응답에 `categories`를 붙인다.
- 인기순(많이 본 순) 정렬은 인기 순위 작업 때 제품별 조회 카운트를 함께 만들어 붙인다(아래 "메인 인기 성분"은 성분 단위라 그대로 쓸 수 없다). 배포 전에는 조회 데이터가 없어 최신순과 같다.

**제품 비교**: 2~3개를 담아 성분을 행, 제품을 열로 놓는다. 성분마다 기준 대비 %와 충족·미달을 표시하고, 가장 많은 값을 강조한다. 없는 성분은 "-". 목록·제품 검색에서 "추가"로 하나씩 담고 빼며, 3개가 찬 뒤 더 담으려 하면 "3개까지만 비교할 수 있어요"를 보여준다. 1개만 담았을 때는 API를 부르지 않는다(2026-11-11).

**함량 표시 규칙**
- 분모를 확인한 값은 "1일 기준", 분모를 확인하지 못한 값(`basis_check`가 `UNVERIFIED`·`UNREADABLE`)은 "표시 기준량" 배지를 단다(디자인 초안, 2026-11-06). 값은 성분표 기준량당 함량 그대로라 "추정"보다 사실에 가깝다. 로컬 기준 원료 제외 제품의 77%다. 이 비율을 줄이는 일은 따로 시간을 들여 개선한다.
- 1일 함량을 모르는 행(원료 제외 성분 행의 약 1.2%, `/g` 분모에 중량 없음·환산 규칙 없는 단위)은 숨기지 않는다. 막대·기준치 % 없이 성분표 원문 값을 보여주고 함량순 정렬에서 맨 뒤에 둔다. 함량 범위 필터에서는 빠진다.
- 한 성분 안에 단위가 섞인 성분(엽산 DFE·mg, 비타민 A RAE·RE·mg, 나이아신 NE·mg, 비타민 E α-TE·mg)은 원료(합성/천연 등)를 몰라 환산하지 않는다. 주 단위(`ingredient.default_unit`)를 정해 함량순은 주 단위 값 → 다른 단위 값 → 모르는 값 순, 함량 범위는 주 단위 값에만 건다. 화면은 단위가 주 단위와 다르면 "다른 단위 표기"로 구분한다(2026-11-08).
- 1일 기준: 비타민·무기질은 **영양성분 기준치 100% 이상**, 기능성 원료는 **고시 1일 섭취량 최소값 이상**이면 충족이다. 성분별 기준값·상한은 `ingredient`에 칼럼으로 두고, 출처는 `docs/daily-reference.csv`에 남긴다. "상한 초과" 배지는 달지 않는다(2026-11-06). 대신 1일 함량이 상한의 2배를 넘으면 오류로 의심해 "검수 대기" 경고를 단다. 저장하지 않고 응답 때 계산한다(2026-11-09). 상한은 비타민·무기질은 상한섭취량, 기능성 원료는 고시 1일 섭취량 최고값이다(일부 제외, `docs/daily-reference.csv`).
- 같은 제품에 같은 성분 행이 여러 개면(로컬 505쌍, 217개 제품) **합치지 않고 모두 보여준다**("5.95mg + 2.55mg"). 원문 표본 조사(2026-11-07) 결과 원인이 섞여 규칙 하나로 맞출 수 없다.
  - 약 72%(361쌍)는 멀티팩의 구성품별 성분표다. 합산이 맞다. 값이 완전히 같은 쌍(116쌍)도 88쌍이 멀티팩이라 "같은 값 = 중복"도 아니다.
  - 나머지는 같은 내용의 중복 기재다. 수출국별 규격(`[말레이시아]`·`<영국>`), 원료용/최종제품용 규격, 유산균 합계와 일부(`프로바이오틱스 수`·`유산균 수`), 1정 기준과 1포 기준. 하나만 맞고 합산하면 부풀려진다.
  - 어느 구성품·국가의 값인지 지금 데이터에 없어 자동으로 가를 수 없다. 정확히 합치려면 파서가 구간을 나눠 `product_ingredient`에 칼럼을 둬야 한다(파서 버전 업 + 재적재). 영향이 제품의 0.5%라 관리자 검수 뒤로 미룬다.
  - 검색 함량순은 가장 큰 값 하나로 정렬한다(멀티팩은 실제보다 낮게 정렬된다). 비교의 "가장 많은 값 강조"는 제품마다 행이 하나이고 단위가 같은 성분에만 한다.

**브랜드 사전**: 사용자는 제조사보다 브랜드로 찾고 비교한다. 성분 사전과 같은 방식으로, 제품명에서 브랜드 후보를 뽑아 CSV로 검토한 뒤 Flyway로 넣는다. 이름에 브랜드가 없는 제품(예: "눈에는 눈 NOON")이 있어 연결률을 실측한다. 같은 이름 제품이 신고번호만 다르게 여러 개 있는 경우(예: "비타민C 4000 영국산" 3건) 목록에서 묶을지도 이때 정한다.

정함(2026-11-12, V13):
- 식약처 공개 데이터(I0030, C003, 생산실적, 판매업 인허가)에는 제품별 판매사(유통전문판매원) 칸이 없다. 브랜드는 제품명에서만 뽑는다.
- 범위는 "제품명에 보이는 브랜드"다. 제품명이 표기로 시작하면 연결하고(가장 긴 표기 우선), 이름 중간은 보지 않는다. 회사가 브랜드로 내세우는 라인(락토핏, 듀오락, 화애락 등)도 독립 브랜드로 둔다.
- 검토(`docs/brand-dictionary.csv`, 근거 URL 포함)에서 접두어 일괄 연결이 위험한 표기는 보류했다(한미, 안국, 동국, 유한M 등). 보류 표기는 `brand_id` NULL로 사전에 남겨, 더 짧은 표기로 잘못 연결되지 않게 한다("유한M …"이 "유한" → 유한양행으로 가지 않음).
- 운영사(여에스더·닥터에스더 → 에스더포뮬러)와 제품별 수동 지정은 두지 않는다. 운영사는 쓸 화면이 생기면 `brand`에 칸을 더하고, 제품별 지정은 관리자 검수(4단계)에서 한다.
- 연결률은 로컬 원료 제외 제품 43,449개 중 5,326개(12.3%)다. 화면은 브랜드 없는 제품을 기본으로 둔다.
- API(2026-11-12): 제품 응답의 `brand`(`{id, name}`, 없으면 null), 검색어가 브랜드 표기와 정확히 맞으면 그 브랜드 제품을 더하고 `matchedBrand`로 알린다, 성분별 목록 `brand=`(OR), 브랜드 목록 `GET /api/brands`(공개 제품이 있는 브랜드, 제품 수 순).
- 같은 이름 제품은 묶지 않는다. 이름이 겹치는 6,501개(2,647종)의 대부분이 "밀크씨슬"(29개, 제조사 28곳)처럼 다른 회사의 일반 이름이다.

**수출용 제품**(2026-11-13): 제품명 표기("수출" 포함, 단 수출겸용·수출명 제외 / 괄호 안 국가명만)로 `ExportName`이 판정해 V14 `product.export_only`에 저장한다. 로컬 원료 제외 제품의 6.0%(2,608개). 응답 `exportOnly`(화면은 "수출용" 배지), 검색·성분별 목록의 `market`(기본 `all`은 모두 보여주되 수출용을 뒤로, `domestic`, `export`), 브랜드 목록은 국내·수출 수를 나눠 국내 수로 정렬.

## 인증

- Spring Security OAuth2 Client, 카카오·네이버·구글. 제공자를 추상화해 추가가 쉽게 한다.
- 이메일은 회수 알림에 필요하다. 이메일이 없거나 동의하지 않은 경우 로그인 후 입력받는 화면을 둔다.
- 여러 제공자로 가입한 같은 사람의 계정은 MVP에서 자동 병합하지 않는다.
- 카카오 연결 해제 웹훅·네이버 연결끊기 알림을 받으면 해당 소셜 계정과 회원 정보를 삭제한다(멱등). 공개 HTTPS 주소가 필요하므로 배포 후 등록.
- 인앱 브라우저에서 구글 로그인이 막힐 수 있다. 대응 방식은 미해결.
- 로그인 상태는 세션으로 유지한다(JWT 안 씀, 2026-11-07). OAuth2는 콜백에서 한 번 본인을 확인할 뿐이고, 그 뒤 요청은 Spring Security 세션 쿠키로 알아본다.
  - 저장소는 `spring-session-jdbc`(Postgres). 기본값(api 메모리)이면 배포·재시작 때 모든 사용자가 로그아웃된다. 서버가 늘어도 공유 저장소라 그대로 쓴다.
  - JWT를 안 쓰는 이유: 연결 해제 웹훅·탈퇴·관리자 권한 회수 때 즉시 무효화해야 한다. JWT는 만료 전까지 취소가 어렵고, 차단 목록을 두면 결국 저장소 조회라 세션과 같다.
  - Redis를 캐시로 도입하면 세션 저장소도 `spring-session-data-redis`로 옮길 수 있다(로그인 코드는 그대로).
  - 쿠키 기반이라 CSRF 보호를 켠다. CloudFront가 `/api/*`에 쿠키를 넘기도록 설정한다.

## 구매 링크

- 자체 API가 링크를 내려준다(링크 정책 변경, 클릭 로그, 키 보호).
- MVP는 수동 등록 링크. 쿠팡 파트너스 API는 최종 승인(누적 판매 15만원 초과) 후.
- 구매 버튼 근처에 대가성 문구를 표시하고, 수수료가 순위·노출에 영향을 주지 않는다.

## 관리자 운영 도구 (MVP 다음)

자동 판정으로 끝나지 않는 데이터가 실제로 쌓인다(초기 적재 기준 `NEEDS_REVIEW` 300, `NO_AMOUNT` 1,062, 번호로 매칭되지 않는 회수 약 56%). 이걸 DB를 직접 고치지 않고 처리할 화면과 API를 만든다. 사용자는 운영자 본인뿐이다.

- 파싱 검수 대기열: `NEEDS_REVIEW`·`NO_AMOUNT` 제품을 원문 `STDR_STND`와 파싱 결과를 나란히 보고 고친 뒤 `REVIEWED`로 바꾼다. 재수집이 `REVIEWED`를 덮지 않는 건 `Product.applyParse`가 이미 지킨다.
- 회수 매칭 검수: `RecallMatchCandidate` 수락·거절.
- 수집 현황: 출처별 커서, 마지막 실행 시각·건수·실패 여부, 수동 실행 버튼.
- 수동 실행 방식: API는 `collect_request`에 `PENDING` 한 줄만 쓴다. EC2 cron이 1분마다 `PENDING`을 확인해 `RUNNING`으로 바꾸고 batch 컨테이너를 띄우며, batch가 끝나면 `DONE`/`FAILED`와 건수를 남긴다. 새벽 정기 수집도 cron이 같은 테이블에 요청을 넣어 같은 경로로 돈다. API에 Docker 소켓이나 AWS 권한을 주지 않으려는 것이고, 요청 행이 그대로 수집 이력이 된다. 버튼 후 시작까지 최대 1분 걸린다.
- 권한: `Member.role`(`USER`/`ADMIN`). `/admin/**`은 `ADMIN`만, 서비스 메서드에도 `@PreAuthorize`. 관리자는 소셜 로그인 + 허용 목록이 주된 보호이고, Nginx `/admin` IP 제한은 보조(집 IP가 바뀔 수 있음). 역할 세분화(검수 전용 등)는 운영자가 늘면 추가.
- 감사 로그: `admin_audit_log`에 누가·언제·무엇을·전후 값을 남긴다. 변경과 같은 트랜잭션에서 기록하고, 추가만 한다(수정·삭제 없음).
- 화면(2026-11-15 정함): 프론트(Next.js) 안의 `/admin`. 별도 관리자 앱을 두지 않는다. 집 아이패드 가로(약 1180px)를 기준 화면으로 잡는다(검수가 원문·파싱 결과를 나란히 보는 화면이라 맞는다). 아이패드는 Safari "홈 화면에 추가"로 쓰고 따로 앱을 만들지 않는다.
- 보기와 조작을 나눈다: 지표·로그를 보는 건 Grafana(아래 "모니터링·알림"), 데이터를 바꾸는 건 관리자 웹 + `/admin/**`. Grafana에는 버튼·권한·감사 로그를 붙이지 않는다.
- 하지 않는 것: 별도 관리자 서버, 외부 인증 서버(Keycloak 등), 리소스별 권한 테이블, 자체 MFA(소셜 제공자의 2단계 인증으로 대신).

## 모니터링·알림 (2026-11-15 정함)

대시보드보다 알림이 먼저다. 사용자가 적을 때는 대시보드를 매일 보지 않고, "배치가 실패했다", "회수 메일이 안 나간다"를 바로 알아야 한다.

- 구성: 모니터링 전용 EC2(t4g.small로 시작, 실측 후 조정)에 Grafana + Prometheus + Loki를 직접 운영한다. 앱 EC2에는 수집 에이전트 Grafana Alloy만 둔다. 앱 EC2의 2GB에 같이 올리면 `mem_limit` 합계(1,856MB)를 넘는다. Grafana Cloud(관리형)는 비교 후 직접 운영 경험을 위해 택하지 않았다.
  - 비용: 서버가 한 대 늘어 ADR-004 예산(월 3만원)을 넘는다. 모니터링 EC2를 띄울 때 ADR-004를 고친다.
- 연결 방향: 앱 EC2의 Alloy가 모니터링 EC2로 밀어 보낸다(push). 앱 EC2는 인바운드 0개를 유지하고, 모니터링 EC2는 같은 VPC의 앱 EC2 보안 그룹에서 오는 수집 포트만 받는다.
- 접속: Grafana를 인터넷에 공개하지 않는다. Tailscale로 모니터링 EC2와 운영자 기기(맥, 아이패드)를 사설망으로 묶는다. 아이패드 현황판은 Grafana `?kiosk` + 자동 새로고침.
- 데이터 출처: 요청·JVM·커넥션 풀은 Micrometer Prometheus 엔드포인트, 호스트·컨테이너는 Alloy, 로그는 JSON 구조화 로그 → Loki. 수집·회수·사용자 숫자는 대부분 DB에 이미 있어 Grafana에 Postgres를 읽기 전용 계정으로 붙여 SQL로 그린다(앱 코드 변경 최소).
- 대시보드(★는 알림도 건다):
  1. 서비스: 요청 수, 5xx 비율★, 엔드포인트별 p95(검색·비교·상세), 헬스★, 마지막 배포 sha
  2. 서버 자원: 컨테이너별 메모리·CPU, swap, 디스크★, JVM 힙·GC, Hikari 풀, Postgres 크기. medium 증설 판단 근거
  3. 수집 파이프라인(출처: batch 실행 기록 `job_run`, 2026-11-18): 작업별 마지막 성공 시각★(예: 회수 수집 26시간째 성공 없음. batch가 직접 알리지 않고 Grafana가 "성공이 안 보임"을 잡아 실패·미실행을 함께 잡는다), 처리·신규·변경 건수, 식약처 API 오류 코드, 검수 대기(`NEEDS_REVIEW`·`NO_AMOUNT`), 사전 연결률
  4. 회수 알림: 신규 회수, 자동 매칭·검수 대기, Outbox 미발송 수·최장 대기★, SES 발송·반송★·수신 거부(반송이 늘면 SES 계정 정지 위험)
  5. 사용자·제품: 가입자, DAU, 서랍 담기, 알림 구독자, 인기 성분·검색어, 0건 검색어(사전 누락 동의어 찾기), 구매 링크 클릭
- 알림:
  - 주: Grafana Alerting → Slack. 대시보드 숫자 그대로 조건을 건다. 채널은 `#alkkuni-장애`(긴급, 휴대폰 알림)와 `#alkkuni-배치`(급하지 않음).
  - 보조: CloudWatch 알람 → SNS → AWS Chatbot → 같은 Slack. Grafana가 볼 수 없는 것만 맡는다: 두 EC2의 상태 검사 실패(모니터링 서버가 죽으면 Grafana 알림도 멈춘다). 상태 검사는 EC2 기본 지표라 따로 보내지 않는다. 앱 지표를 CloudWatch에도 보내지 않는다(같은 장애로 알림이 두 번 온다).
  - n8n은 지금 두지 않는다. Slack은 Grafana가 직접 보낸다. 아침 요약, 카카오톡, Slack 버튼 → 관리자 API 연동이 필요해지면 모니터링 EC2에 추가한다(부품이 하나 늘고 알림 경로가 길어진다).
- 순서: 기본 배포 메모리 실측 → 2~3단계에 계측(Micrometer, 구조화 로그, 모니터링 EC2, 서비스·서버 대시보드) → 4단계 공개 전 알림(★) → 공개 후 1~2주 사용자·비즈니스 대시보드 → 5~6주차 관리자 웹과 함께 수집·회수 대시보드 정리.

## 보안 운영

사고가 난 뒤에 고치는 것에 그치지 않도록, 아래 항목을 미리 넣어 두고 PR마다 같은 기준으로 점검한다.

- 실제 사용자 IP 복원: CloudFront 뒤라 Nginx가 보는 연결 IP는 모두 CloudFront다. `real_ip_header X-Forwarded-For`(recursive 끔)로 CloudFront가 맨 끝에 붙인 값만 쓴다. 클라이언트가 앞에 꾸며 넣은 값(XFF 위조)은 무시된다. 이게 없으면 아래 호출 제한과 IP 제한이 CloudFront 단위로 걸린다. api·web에는 받은 헤더를 이어 붙이지 않고 골라낸 IP 하나(`$remote_addr`)만 넘긴다. 이어 붙이면 맨 앞에 꾸민 값이 남아 뒤에서 맨 앞을 사용자 IP로 읽으면 속는다.
  - `set_real_ip_from`은 `0.0.0.0/0`(2026-11-18 정함). 직접 접속은 보안 그룹이 막으므로 Nginx에서 연결 IP를 다시 따지지 않는다. CloudFront 대역을 나열하면 AWS가 대역을 바꿀 때마다 손으로 고쳐야 한다. 대가는 보안 그룹이 잘못 열리면 헤더를 꾸며 호출 제한을 피할 수 있다는 것(인증·권한은 IP와 무관).
  - `X-Forwarded-Proto`는 CloudFront~Nginx가 HTTP라 지금 `http`로 넘어간다. 전체 URL을 만드는 곳(소셜 로그인 리다이렉트)이 생기는 3단계 인증 PR에서 Host 전달·`forward-headers-strategy`와 함께 맞춘다. 그 전제로 CloudFront는 HTTP를 HTTPS로 리다이렉트한다.
- 직접 접속 차단: EC2 보안 그룹의 80/443은 CloudFront 관리형 prefix list만 허용한다. EC2 IP로 바로 와서 헤더를 꾸미는 요청을 막는다.
- 호출 제한(rate limit)은 두 겹으로 둔다(2026-11-18 정함).
  - 1겹 Nginx `limit_req`(사이트 공개 때, CloudFront PR): 모든 요청을 실제 사용자 IP 단위로 센다. 처음 값은 `10r/s`·`burst=20 nodelay`(넉넉하게 두고 공개 뒤 로그로 조인다). `/api/`·페이지(`/`)·`/actuator/health`(CloudFront 기본 동작으로 외부에 열림)를 세고 `/_next/static/`(해시 붙은 정적 파일)만 뺀다. Next 링크 미리 불러오기(`Next-Router-Prefetch`·`Next-Router-Segment-Prefetch` 헤더)는 보이는 링크마다 요청이 나가 일반 통을 바로 넘기므로 따로 넉넉한 통(`30r/s`·`burst=100`)에서 센다. 요청 하나는 두 통 중 하나에만 들어가고, 헤더를 꾸며도 미리 불러오기 통으로 옮겨 갈 뿐 상한은 남는다. 미리 불러오기가 web CPU를 많이 쓰면 프론트에서 목록 링크의 `prefetch`를 끈다. 서버 컴포넌트는 `api:8080`을 직접 불러 Nginx를 안 거치므로 페이지 요청이 백엔드 부하의 관문이다. 로그인과 상관없이 크롤러·반복 호출을 앱에 닿기 전에 막고, 넘치면 429(`limit_req_status 429`, 기본은 503). 화면 한 번에 요청이 여러 개라 `burst`를 둔다. 소셜 연결 해제 웹훅 경로는 제공자 서버 IP에서 몰려 올 수 있어 웹훅 PR(3단계)에서 이 제한에서 뺀다(웹훅은 서명 검증으로 막는다). IP 단위의 한계: 통신사 NAT 뒤 여러 명이 한 통을 쓰고, IPv6는 주소를 바꿔 가며 피할 수 있다. 공개 뒤 로그로 한도를 조인다.
  - 2겹 앱 Bucket4j(3단계 인증 뒤): IP로는 구분할 수 없는 "회원 한 명"을 기준으로, 쓰기·비싼 요청에만 건다. 서랍 담기·알림 설정 변경, 이메일을 보내는 요청(이메일 인증 등), 후기 작성(생기면), AI 도우미(생기면, 호출마다 비용). 같은 회원이 휴대폰 데이터·와이파이로 IP를 바꿔도 같은 통에서 줄어든다. 비로그인 요청은 Nginx에 맡기고 앱에서 다시 IP로 세지 않는다(같은 일을 두 번 하게 된다).
  - 키는 `member.id`, 버킷은 API별로 따로(서랍 쓰기와 AI 도우미 한도가 다르다). 위치는 Spring Security 인증 뒤의 `HandlerInterceptor`(경로별 한도). 넘치면 429와 `Retry-After` 헤더, 응답 본문은 `ApiResponse` 오류 코드 `TOO_MANY_REQUESTS`(`GlobalExceptionHandler`에 추가).
  - 저장소: api가 한 대라 메모리(Caffeine으로 오래 안 쓴 버킷을 비움). 재시작하면 통이 다시 차는데, 배포 때 한 번이라 문제없다. api가 두 대 이상이 되면 공유 저장소(Bucket4j PostgreSQL 연동 또는 Redis 도입 시 Redis)로 옮긴다. 그 전엔 서버마다 따로 세서 한도가 대수만큼 커진다.
  - 한도 값은 정하지 않는다. 공개 뒤 정상 사용 패턴(회원당 분당 요청 수)을 지표로 보고, 그 몇 배로 잡는다. 처음엔 넘쳐도 막지 않고 로그만 남기는 모드로 며칠 돌려 정상 사용자가 걸리지 않는지 본다.
  - 테스트: 한도를 넘기면 429·`Retry-After`, 다른 회원은 영향 없음, 비로그인 요청은 앱 제한을 거치지 않음.
  - 엣지 0겹 AWS WAF 속도 제한(2026-11-18 바꿈): CloudFront 무료 요금제에 추가 비용 없이 들어 있어, 처음 "월 고정 비용"(ADR-004)으로 뺐던 이유가 없어졌다. IP당 5분 1000건, 폭주만 EC2 밖에서 거르는 굵은 그물이고 세밀한 제한은 Nginx가 맡는다. WAF는 캐시로 답한 정적 파일까지 세서(페이지 한 번에 30~50건) 기본값 300은 정상 사용자가 걸린다. 처음엔 모니터 모드로 CloudWatch 지표만 보고, 정상 사용자가 안 걸리면 차단으로 바꾼다. 관리형 기본 보호(흔한 취약점, IP 평판)는 차단 모드. 오탐이면 화면에 우리 429가 아닌 CloudFront 403이 뜬다(예: 공통 규칙의 8KB 넘는 요청 본문).
  - 하지 않는 것: 지금(로그인 전) 앱 계층 IP 제한.
- 소셜 연결 해제 웹훅은 서명·출처 검증을 테스트로 남긴다.
- GitHub Dependabot·secret scanning을 켠다.
- `REVIEW.md`에 보안 체크리스트를 두고, 위험 경로 PR은 `/security-review` 결과를 PR에 남긴다.
- 회원 탈퇴 시 개인정보 삭제를 테스트로 증명한다.

## 배포

- 프론트·백엔드 레포와 CI/CD 분리. 이미지는 각 레포 CI가 만들어 ECR에 커밋 sha 태그로 올리고, EC2는 받아서 띄우기만 한다.
- 운영 파일도 레포별로 나눈다(2026-11-18 정함, 2026-11-09 "compose 하나를 백엔드 레포에" 결정을 바꿈).
  - 백엔드 레포: `compose.prod.yaml`(nginx·api·batch·db, 프로젝트 `alkkuni`), `deploy/nginx`, `deploy.sh`. 태그는 EC2 `.env`의 `API_TAG`·`BATCH_TAG`.
  - 프론트 레포: web 전용 compose(프로젝트 `alkkuni-web`)와 배포 스크립트. EC2에서는 `/opt/alkkuni/web/` 아래에 따로 두고(백엔드의 `.prev/`·`.next/`와 섞이지 않게), 태그는 그 안 `web.env`의 `WEB_TAG`. 프론트 CI가 SSM으로 그 sha의 배포 스크립트를 부른다.
  - 이유: compose·`.env`가 하나면 백엔드 배포가 `.env`를 다시 만들거나 롤백하면서 `WEB_TAG`를 지우거나 옛 값으로 되돌린다. 파일을 나누면 한쪽 배포·롤백이 다른 쪽을 건드리지 않는다. web compose를 프론트 레포에 두면 이미지와 같은 sha의 배포 파일을 받아 버전이 어긋나지 않는다.
  - 두 레포의 약속: 네트워크 `alkkuni_default`(백엔드 프로젝트 기본 네트워크, web이 external로 들어옴. 이름을 바꾸면 롤백이 깨진다), 서비스 이름 `web`, 포트 3000. 메모리 한도는 레포가 나뉘어 있어 합계(2GB)를 양쪽 compose 주석에 적는다.
  - 별도 infra 레포는 지금 규모에 과하다.
- Nginx 라우팅: `/api/*`·`/actuator/health`는 api 컨테이너로, 나머지(`/`)는 web(Next.js) 컨테이너로 넘긴다.
- 기본 배포 범위(2026-11-09 정함): Nginx(위 라우팅만) + api + batch + db. web이 아직 없어서 `/`는 502가 나도 된다. 보안 그룹 80·443은 닫아 두고, 헬스 체크는 SSM으로 EC2 안에서 Nginx를 거쳐(`curl localhost/actuator/health`) 한다. batch는 초기 적재와 메모리 실측(batch 실행 중 `docker stats`·swap 피크) 때문에 함께 올린다.
  - CloudFront를 붙일 때 한꺼번에 넣는 것: `set_real_ip_from`·`real_ip_header`, `limit_req`, 보안 그룹을 CloudFront prefix list로 열기. `/admin` IP 제한은 `/admin`이 생길 때 넣는다.
  - CloudFront 요금제(2026-11-18): 무료 고정 요금제. 캐시 동작 5개(3개 사용), 도메인 1개, WAF 규칙 5개, 월 약 100만 요청 기준(페이지 방문 하루 약 700~1,000회). 액세스 로그·봇 분석은 Pro부터라 실제 IP 로그는 Nginx에서 본다. 기본 DDoS(Shield Standard)는 요금제와 상관없이 적용된다. 사용량이 기준을 넘거나 액세스 로그가 필요해지면 Pro($15/월)를 본다.
  - CloudFront 동작(2026-11-18, PR #45 리뷰로 고침). 원본은 탄력적 IP의 퍼블릭 DNS, HTTP 80. 뷰어는 HTTP를 HTTPS로 리다이렉트.

    | 경로 | 캐시 정책 | 원본 요청 정책 | 허용 메서드 |
    |---|---|---|---|
    | `/_next/static/*` | `CachingOptimized` | 없음 | GET, HEAD |
    | `/api/*` | `UseOriginCacheControlHeaders-QueryStrings` | `AllViewer` | 전부 |
    | 기본(`/`) | `CachingDisabled` | `AllViewer` | 전부 |

    - 원본 요청 정책을 비워 두면 CloudFront가 헤더·쿠키를 대부분 빼고 넘겨 Next 화면 이동(`RSC` 헤더)·Server Action·세션 쿠키가 깨지고, 기본 메서드(GET/HEAD)라 POST는 403이 난다. 원본 요청 정책은 "넘길 것"만 정하고 캐시 키는 캐시 정책이 정하므로 쿠키를 넘겨도 `/api/*` 캐시가 사용자별로 갈라지지 않는다. 회원마다 다른 응답의 `private`·`no-store`는 위 "캐시" 규칙 그대로.
    - 페이지는 CloudFront에 캐시하지 않는다. Next는 정적 페이지에 `s-maxage=31536000`을 붙일 수 있어, 원본 `Cache-Control`을 따르면 프론트 재배포 뒤에도 옛 HTML이 남고 그 HTML이 가리키는 옛 `/_next/static` 파일이 새 컨테이너에 없어 404로 화면이 깨진다. 같은 URL에 HTML과 RSC 응답이 섞여 캐시될 위험도 함께 없어진다. 대가는 페이지 요청이 매번 EC2까지 오는 것(응답 지연, 트래픽 급증을 Nginx 제한과 t4g.small이 받음). 무거운 정적 파일은 계속 CloudFront가, API는 60초 캐시가 받는다. 페이지 응답 시간이나 web CPU가 문제가 되면 프론트 배포마다 CloudFront 무효화를 넣고 페이지 캐시를 켠다.
- 이미지(2026-11-13): Dockerfile 하나(`ARG MODULE`)로 api·batch를 만든다. jar는 CI가 Gradle로 먼저 빌드한다. 운영 구성은 `compose.prod.yaml`, Nginx 설정은 `deploy/nginx/default.conf`.
- 배포는 서비스 단위 교체(`docker compose pull api && docker compose up -d --no-deps api`). `docker compose down`은 배포에 쓰지 않는다.
- CI/CD 단계: (1) 테스트·빌드·ECR 푸시 → (2) SSM으로 교체 → (3) 헬스 체크(`/actuator/health`) 실패 시 직전 태그로 자동 롤백.
- 컨테이너별 `mem_limit`, JVM 힙 크기 조정. 2GB가 부족하면 t4g.medium 검토.
- 인스턴스(2026-11-07 정함): t4g.small로 시작하고 기본 배포 때 메모리를 실측한다. 부족하면 중지 → 인스턴스 유형 변경 → 시작으로 medium에 올린다(EBS 데이터 유지, 같은 t4g(ARM) 안에서만). medium은 월 약 5만원으로 ADR-004 예산(월 3만원)을 넘으니 올릴 때 ADR-004를 고친다.
  - 처음부터 탄력적 IP를 붙인다. 중지·시작하면 일반 공인 IP가 바뀌어 CloudFront 원본이 끊긴다.
  - swap 파일 1~2GB를 안전망으로 둔다(`swappiness` 낮게). batch가 도는 동안 OOM killer가 Postgres·api를 죽이는 것을 막는 용도다. swap을 꾸준히 쓰면 증설 신호다. 컨테이너 `mem_limit`은 swap과 별개로 넘으면 죽는다.
  - RDS는 지금 쓰지 않는다. 같은 돈이면 medium이 메모리를 더 준다. 서버 2대 이상, 하루치 데이터 손실 불가, Multi-AZ가 필요해지면 DB부터 RDS로 뺀다.
- 백업(2026-11-07 정함): 매일 cron으로 `pg_dump` → S3, 수명 주기로 30일 안팎 보관. 제품·성분은 식약처에서 다시 받을 수 있지만 회원·서랍·알림 내역·검수 결과·감사 로그는 되살릴 수 없다. 복구 훈련: 빈 Postgres 컨테이너에 복원하고 행 수를 원본과 대조, 걸린 시간을 기록한다. 시점 복구는 안 된다(최대 하루치 손실).

## 캐시

순서(2026-11-07 정함): 브라우저 캐시 → CloudFront 캐시 → Redis. 앞 단계가 싸고, 뒤로 갈수록 메모리·운영 부담이 든다.

- 공개 조회 API(검색·비교·상세·성분별 목록): 성공 응답에 `Cache-Control: public, max-age=60`. 식약처 데이터는 하루 한 번 바뀌어 60초 지연은 문제없다. 같은 사용자의 뒤로 가기·재방문이 빨라진다(여러 사용자 사이 부하는 못 줄인다).
- CloudFront를 붙일 때 `s-maxage=60`과 공개 조회 경로의 캐시 정책을 켠다. 여러 사용자의 같은 요청을 CloudFront가 대신 답한다.
- 회원마다 다른 응답(서랍, 마이페이지, "서랍에 담김" 표시가 섞인 응답)은 `no-store` 또는 `private`. `public`으로 CloudFront에 캐시되면 남의 응답이 보인다. 서랍 여부는 별도 API로 나눈다.
- 에러 응답(404·500)은 캐시하지 않는다.
- Spring Security는 기본으로 모든 응답에 `no-cache, no-store`를 붙인다. 인증을 넣을 때 공개 조회 API의 헤더가 덮이지 않는지 테스트로 막는다.
- Next.js 정적 파일(해시가 붙은 JS·CSS·아이콘)은 Next.js 기본값(1년, `immutable`).
- Redis는 위로도 느린 쿼리가 남을 때(`EXPLAIN ANALYZE`로 확인) 캐시로 들인다. 메모리를 쓰므로 small 메모리 실측 뒤.

## 메인 인기 성분 (2026-11-12 정함, 2026-11-18 순위 계산 방식 바꿈)

1. 지금(MVP): 프론트 메인(`/`)이 고정 성분 6개를 띄운다. 성분은 연결된 제품 수가 많은 순서(로컬 2026-11-12: 아연 12,349, 비타민 D 9,778, B6 8,413, B1 8,054, B2 7,617, C 7,344)이고 모두 기준치가 있다. API는 새로 만들지 않고 프론트가 기존 성분별 목록 API(`size=3`, 성분 함량순)를 성분마다 부른다. 성분 목록은 프론트 상수다. 랜덤으로 띄우지 않는다(사전 대부분이 낯선 성분이고, 매번 바뀌면 캐시를 못 쓴다).
2. 다음(백엔드): 조회 기반 인기 순위를 만들고 성능을 잰다.
   - 날짜별 카운트 테이블 `(view_date, ingredient_id, count)`, PK `(view_date, ingredient_id)`. 볼 때마다 `INSERT ... ON CONFLICT DO UPDATE SET count = count + 1`. 행 수가 "날짜 × 성분 수"로 묶여(1년 215 × 365 ≈ 8만) 오래된 기록을 지우지 않아도 되고, "최근 7일"도 셀 수 있다. 볼 때마다 한 줄씩 쌓기(기간은 자유롭지만 계속 커짐)와 성분별 누적 숫자 하나(예전 인기가 위에 남음)는 쓰지 않는다.
   - 순위는 미리 계산하지 않는다. `GET /api/home/popular`(이름은 안)가 요청을 받을 때 카운트 테이블의 최근 7일을 `GROUP BY ingredient_id`로 합쳐 상위 몇 개를 돌려주고, 응답에 `Cache-Control: public, max-age=60, s-maxage=60`을 붙인다(위 "캐시"의 `s-maxage` 방침). 전제는 CloudFront 캐시 정책에 이 경로가 들어 있는 것이고(2단계 CloudFront 연결 때 같이 켠다), 그 전에는 요청마다 집계가 돈다(수 ms라 문제는 없다). CloudFront가 이 응답을 60초 보관해 모든 사용자에게 같이 내주므로 사용자 수와 상관없이 집계는 1분에 최대 한 번(엣지별)이고, 아무도 안 들어오면 집계도 없다. 집계 대상은 7일 × 조회된 성분 수(많아야 약 1,500행)라 수 ms다. 대가는 순위가 늦게 바뀐다는 것이다. CloudFront 60초에 브라우저 `max-age` 60초가 겹쳐 최대 약 2분(배치는 최대 하루). 프론트가 이 API를 서버 캐시(`"use cache"`)로 감싸면 기본 `cacheLife`(15분)가 더해지므로, 프론트는 `cacheLife`를 60초 이하로 두거나 서버 캐시를 쓰지 않는다. 기록이 없거나 모자라면 1의 고정 목록을 돌려준다.
   - 처음엔 하루 한 번 배치(`alkkuni.job=...` + cron)로 순위 테이블을 만들어 두기로 했다(2026-11-12). 집계가 수 ms라 미리 계산할 이유가 없고, 배치 작업·순위 테이블·cron 줄이 모두 없어져 바꿨다(2026-11-18). 기간을 늘리거나(예: 90일) 제품 단위(수만 개)로 넓혀 집계가 실측으로 느려지면 그때 순위 테이블과 배치를 들인다.
   - 조회 기록은 성분별 목록 API 안에서 세지 않는다. 프론트 서버 캐시(`"use cache"`), 응답 `max-age=60`, CloudFront가 앞에서 답해 백엔드가 조회를 거의 못 본다. 브라우저가 따로 보내는 기록 요청(예: `POST /api/views`, 캐시 안 함)이 필요하고, 무엇을 셀지(목록에서 고른 성분, 검색어에 잡힌 성분, 상세에서 본 제품의 성분)와 새로고침 반복·봇 거르기는 이 작업 때 정한다.
   - 성능: k6로 같은 날 같은 성분에 기록 요청을 몰아 카운트 `UPDATE`의 행 잠금 대기와 응답 시간을 재고 노션 "성능 개선"에 남긴다.
3. 결과를 보고 정한다.
   - DB로 충분하면 그대로, 잠금 대기가 응답에 보이거나 실시간 순위가 필요하면 Redis Sorted Set(`ZINCRBY popular:ingredients:{날짜}`, 날짜 키 TTL, 최근 7일은 `ZUNIONSTORE`)으로 카운트만 옮긴다. 그때 순위는 Redis에서 바로 읽고, 날짜별 카운트는 하루 한 번 DB로 옮겨 남긴다(이 경우에만 배치가 생긴다). 캐시용 Redis(위 "캐시")가 이미 들어와 있으면 인프라 부담이 없어 옮기기 쉽다. 어느 쪽이든 `GET /api/home/popular` 응답은 같아 프론트는 영향이 없다.
   - 프론트는 배포 뒤 실제 기록이 쌓이면 고정 목록 대신 `GET /api/home/popular`에서 성분 목록을 받는다(카드 코드는 그대로). 그 전에는 API도 고정 목록을 돌려주므로 바꿀 이유가 없다.

## 메인 통계·소식 API (2026-11-15 정함)

프론트 메인이 자리만 비워 두고 기다리는 두 API다(프론트 `docs/PROGRESS.md` "백엔드에 걸린 것"). 둘 다 이미 적재된 데이터를 읽기만 한다.

1. 통계 `GET /api/stats`(이름은 안)
   - 응답: 수록 제품 수, 성분 수, 데이터 기준일. 메인 "공식 데이터로 만들어요" 칸과 푸터 "기준일 YYYY.MM.DD"에 쓴다.
   - 기준일은 `ingestion_cursor`의 `I0030` `last_collected_date` - 1일이다. 커서는 수집을 실행한 날(KST 새벽)이라 그대로 쓰면 반영 안 된 그날까지 포함된 것처럼 보여, "이 날짜까지 반영"으로 맞췄다(PR #47 리뷰). 적재가 멈추면 기준일이 멈춰 보여, 사용자에게도 데이터가 오래됐다는 신호가 된다.
   - 제품 수는 목록·검색에 나오는 제품과 같은 조건으로 센다(화면 숫자와 목록 개수가 어긋나지 않게).
   - 하루 한 번 바뀌는 값이지만 다른 공개 API와 같은 60초 캐시(`PUBLIC_CACHE`)로 둔다. 매 요청 `COUNT(*)`가 부담이 되면 그때 늘린다(2026-11-20 구현).
2. 소식 목록 `GET /api/news`(이름은 안)
   - 응답 항목: 종류(지금은 회수만, 나중에 공지·기사), 제목(제품명), 제조사, 사유, 등급, 날짜. 최신순, 페이지. 메인은 4건, 전체 보기는 같은 API를 페이지로 넘기는 프론트 `/news`.
   - 회수만 먼저 낸다. 공지·기사는 데이터 출처가 정해진 뒤 종류를 늘린다(응답에 종류 필드를 처음부터 둔다).
   - 정함(2026-11-20):
     - 날짜: I0490 원본의 등록일 `CRET_DTM`을 `recall.registered_at`(V18)에 저장한다(로컬 원본 399건 모두 값이 있다. 형식은 `yyyy-MM-dd HH:mm:ss.f`이고 소수점 자릿수만 1~6자리로 다르다). `first_seen_at`은 첫 적재 때 모든 건이 같은 날이라 쓰지 않는다. 회수 수집은 매일 전체 목록을 받아 기존 행을 덮어쓰므로(`Recall.seen`) 배포 다음 새벽에 LISTED 행이 채워진다. 별도 백필 작업 없음
     - 등급: `RTRVL_GRDCD_NM`(1·2·3등급, 자율회수, 빈 값)을 `recall.grade`(V18)에 원문 그대로 저장한다. 식약처가 새 값을 내도 수집이 깨지지 않게 enum으로 만들지 않는다. 빈 값은 null, 화면은 null이면 등급을 숨긴다
     - 범위: 건강기능식품(`product_type = '건강기능식품'`)만. 가공식품·축산물 회수는 서비스와 맞지 않는다
     - `DELISTED`도 남긴다. 목록에서 빠져도 회수 사실은 그대로다. 이미 DELISTED인 행은 다시 받지 않아 등록일이 null로 남고, 정렬은 `registered_at DESC NULLS LAST, id DESC`. 운영 건수를 보고 많으면 `first_seen_at`으로 대신할지 다시 본다
     - 저장소: `news` 테이블을 따로 두지 않고 `recall`을 바로 읽는다. 두 번째 종류가 생길 때 `UNION ALL`(종류 2~3개) 또는 `news` 테이블(직접 쓰는 공지가 섞일 때)을 정한다
   - 다음 종류 후보(2026-11-20): 해외직구 위해식품 차단 정보. 영양제를 해외직구로 사는 사용자가 많고, 회수와 같은 식약처 데이터라 batch 작업 하나로 붙일 수 있다. 식품안전나라 Open API 제공 여부·필드는 아직 확인하지 않았다(착수 때 먼저 조사). 공지는 4단계 관리자 화면에서 등록, 기사는 저작권 때문에 링크만 고려(후순위)
   - 회수 매칭(3단계 병렬) 뒤에는 연결된 제품 상세로 링크할 수 있다. 그 전에는 회수 원문 정보만 보여 준다.
- 순서: 2단계 남은 작업(구매 링크 등)과 함께 한다. 인증과 상관없는 공개 조회 API라 3단계를 기다리지 않는다.

## 리뷰 구조

원칙: 틀리면 안 되는 건 테스트로 막고, 도메인 규칙은 로컬 Claude가, 넓은 시야는 PR의 CodeRabbit이, 위험한 곳은 사람이 본다.

| 단계 | 누가 | 언제 |
|---|---|---|
| 빌드·테스트 | `./gradlew build` (파서 골든 테스트 포함) | 로컬, 모든 PR |
| 도메인 리뷰 | Claude `/code-review` + `REVIEW.md` | 로컬, PR 올리기 전 |
| 보안 리뷰 | Claude `/security-review` | 로컬, 인증·서랍·웹훅·외부 키를 건드린 PR |
| 사람 정독 | 현이 | 위험도 "높음" PR, `REVIEW.md`의 "사람 정독 필요" 경로 |
| CI | GitHub Actions (build + test) | PR, 머지 필수 조건 |
| 교차 리뷰 | CodeRabbit (공개 레포 무료). 자동 리뷰는 끄고 `@coderabbitai review`로 수동 요청(스타 10개 미만 공개 레포는 CodeRabbit이 수동 요청만 허용). 리뷰 한도가 개발자당 시간 단위로 걸리므로 지적 반영은 모아서 푸시한다. 기준은 로컬과 같은 `REVIEW.md`·`CLAUDE.md` | PR |

- 머지 조건: CI 통과, 리뷰 댓글 전부 해결, 승인 0명(혼자라 셀프 승인 불가), 일반 머지(merge commit). 리뷰 반영·수정 커밋까지 `main` 기록에 남겨 작업 과정을 볼 수 있게 한다.
- 리뷰 댓글에는 "고침 / 오탐 / 의도됨"으로 답하고 닫는다. 반복되는 실수는 테스트로, 반복되는 오탐은 `REVIEW.md`·`.coderabbit.yaml`로 옮긴다.
- 하지 않는 것: PR마다 Claude 자동 리뷰(CodeRabbit과 중복), `claude-code-security-review` 액션(API 요금 별도), `@claude` GitHub 연동(1인 개발이라 로컬 Claude Code와 역할이 겹침. 협업자가 생기거나 GitHub에서 질문할 일이 잦아지면 연결). lint는 스타일 지적이 리뷰를 어지럽히기 시작하면 추가.
