# PROGRESS.md

알꾼이 백엔드의 진행 상황이다. **작업 PR 안에서 갱신하고, 머지되면 확정된다.** 머지 후 문서만 고치는 변경을 만들지 않는다.

- PR을 올리기 전: 작업 커밋에 결정 이유, 다음 할 일 정리 등 이미 아는 내용을 넣는다.
- PR을 올린 뒤 머지 전: PR 번호는 PR 생성 후 첫 커밋(보통 `/code-review` 반영 커밋)에 함께 넣는다. 반영할 게 없을 때만 번호 커밋을 따로 한다.
- CI 결과는 적지 않는다. `build`가 필수 체크라 머지됐다는 것 자체가 통과를 뜻한다. 실패를 고친 경우처럼 남길 이야기가 있을 때만 적는다.


- 지금 상태: 이번 주차 목차. 체크 안 된 첫 항목이 다음 작업이다. 해당 PR에서 체크한다.
- 다음 할 일: 항목별로 정할 것과 검증 기준. 끝난 항목은 지우고 "완료"에 날짜와 함께 옮긴다.
- 작업 로그: 결정과 그 이유. 최근 날짜가 위에 온다.

1. 수집 배치 공통
   - Spring Batch는 쓰지 않는다. 배치 작업은 `alkkuni.job=...`으로 켜는 `ApplicationRunner`(한 번 실행 후 종료)로 만들고, 매일 실행은 EC2 cron이 맡는다. 재시작·청크가 필요해지면 Spring Batch 도입

2. 성분 정규화: 1일 함량·단위 통일은 끝남(`daily_amount`). 남은 것은 성분 사전
   - 합의한 방식: `IngredientName.normalize` 키 → `ingredient_alias`(키 → `ingredient_id`) → `ingredient`(대표 이름). 대표 이름은 식약처 건강기능식품 기준·규격 고시 명칭(출처 확인). 사전 초기 데이터는 Flyway로 넣고, 사용자가 CSV 표로 먼저 검토한 뒤 SQL로 확정한다
   - 연결은 판정 버전(`VERSION`)과 분리한다. 사전을 고칠 때마다 식약처 API로 재적재하면 호출 한도에 걸리므로 `link-ingredients` 작업이 DB만 읽어 다시 연결한다
   - 기준 성분이 다른 것은 합치지 않는다(`진세노사이드 Rg1, Rb1 및 Rg3의 합` ≠ `Rg1과 Rb1의 합`)
   - 사전 검토 뒤 V7을 고치면(머지 전) 로컬은 `DELETE FROM flyway_schema_history WHERE version = '7'`, `DROP TABLE ingredient_alias`, `ALTER TABLE ingredient DROP COLUMN iu_per_mg, DROP COLUMN english_name, DROP COLUMN display_name`(CHECK 제약은 칼럼과 함께 지워진다), `UPDATE product_ingredient SET ingredient_id = NULL`, `DELETE FROM ingredient` 후 api를 띄워 V7을 다시 적용하고 `link-ingredients`를 돌린다. 초기화 SQL은 자동 모드 권한에 막혀 사용자가 `!`로 실행한다. 사전·V7은 `data/dict-tools/`(로컬 전용, README에 실행 명령)로 다시 만들고 손으로 고치지 않는다. 머지 뒤 사전 수정은 V8 이후 새 마이그레이션 + `link-ingredients`
   - `U`·`FU`(피브린용해효소 약 130행), 비타민A·E의 IU는 여전히 `daily_amount` NULL. `ingredient.iu_per_mg`에 값을 넣으면 `link-ingredients`가 IU 행을 다시 계산한다
   - 연결 안 된 상위 키는 `link-ingredients` 로그에 20개 나온다. 대부분 파서 조각(`최종제품`, `규격`)이나 원료명(`홍삼`, `EPA및DHA함유유지`)이라 사전보다 파서·검수 대상
   - 1일 함량을 알 수 없는 행 약 1,950건 중 약 940건은 분모가 `/g`인데 섭취방법에 중량이 없다(`1일 2캡슐`). 식약처 다른 API에 1회 중량·내용량 필드가 있는지 조사, 없으면 관리자 검수 대상
   - 정함(2026-11-06, 11-05 "추정" 표시를 바꿈): `UNVERIFIED`·`UNREADABLE`(분모를 확인하지 못한 값)은 "표시 기준량" 배지를 단다. 추정 비율(원료 제외 제품의 77%)을 줄이는 개선은 따로 시간을 들여 한다
   - 검수(`REVIEWED`) 제품은 원문이 같으면 성분 행을 다시 쓰지 않아 섭취방법이 바뀌어도 `daily_amount`가 그대로다. 관리자 검수 흐름을 만들 때 같이 본다
3. 공개 API 공통
   - 검색 API에서 확인한 것(2026-11-07): 함량순·`dailyAmount`는 같은 제품의 같은 성분 행 중 가장 큰 값 하나를 쓴다(비교 API에서 합산 규칙을 정하면 검색도 맞춘다). 한 성분 안에서도 단위가 섞여 있다(엽산 `mg DFE` 2,792행·`mg` 1,700행, 비타민 A `mg RAE`·`mg RE`·`mg`). 함량순은 단위를 보지 않고 숫자로만 정렬하므로 성분별 목록 API 전에 환산 또는 단위별 분리를 정한다
   - `아연` 함량순 1위가 `원기정 셀렌효모` 90mg이다(상한 35mg). 함량순 상위 의심 값 검수는 관리자 검수 흐름에서 본다. 검색 응답에 `basisCheck`·`parseStatus`를 내보내 화면이 "표시 기준량" 배지와 검수 대기 경고를 달 수 있게 했다
   - 2자 검색은 같은 쿼리를 반복하면 느려진다(2026-11-07 실측). PostgreSQL이 6번째 실행부터 검색어를 보지 않는 범용 계획(generic plan)으로 바꿀 수 있는데, 그 계획이 2자에도 GIN을 써 인덱스 전체(46,255건)를 훑는다. `아연` count 42ms → 62ms. 3자 이상(`루테인`)은 어느 계획이든 5~6ms. 응답이 60초 캐시되고 차이가 20ms라 지금은 두고, 운영에서 느리면 JDBC URL `prepareThreshold=0`(모든 쿼리에 적용) 또는 2자 검색만 다른 SQL로 나누는 것을 본다
   - 공개 조회 API 성공 응답에는 `Cache-Control: public, max-age=60`을 붙인다(검색과 같은 방식, PLANNING.md "캐시")
   - 상세 API의 회수 이력은 신고번호가 정확히 같은 건만 붙는다(로컬 건강기능식품 회수 30건 중 12건). 나머지 18건(번호 없음 13, 번호가 우리 DB에 없음 5)은 회수 매칭(검수) 때 `recall.product_id`로 붙이고 상세 조회도 그 기준으로 바꾼다. 회수 날짜는 수집하지 않아 응답에 없다. 같은 회수가 사유만 달리 두 번 올라온 건이 있어(프로폴리스) 화면이 구분하려면 I0490의 등록일 칼럼 수집이 필요하다
   - 인증(3단계) 때 `GlobalExceptionHandler`에서 볼 것(PR #17 리뷰): `@ExceptionHandler(Exception)`이 `AccessDeniedException`·`@ResponseStatus` 예외까지 500으로 바꾼다. 401·403은 지금 `INVALID_INPUT`으로 나가므로 `UNAUTHORIZED`·`FORBIDDEN` 코드를 프론트 연동 전에 추가한다. 500 로그의 예외 메시지에 이메일이 들어갈 수 있다(UNIQUE 위반 `Key (email)=(...)`). 회원 테이블이 생기면 로그 마스킹 또는 해당 예외 별도 처리

- 수출용 제품 표시·정렬·필터(`feat/export-last`, PR #33). 브랜드 검색을 최신순으로 바꾸자 "애터미" 첫 페이지 20개 중 15개가 최근 몰려 신고된 국가별 수출용("석류미인(태국)", "(대만)" …)이 됐다. 국내에서 살 수 없어 지우지는 않고 모든 정렬의 첫 키로 뒤로 보낸다.

### 2026-11-12
- 브랜드 응답·검색·필터(`feat/brand-response`, PR #32). 연결된 5,326개 중 297개(5.6%)는 제품명에 브랜드 이름이 없어("ATOMY …" ↔ 애터미, "유한 …" ↔ 유한양행) 이름 검색으로 안 걸렸다. 검색어를 `BrandName.key`로 바꿔 `brand_alias`와 정확히 맞으면 그 브랜드 제품을 결과에 더하고, 관련도순에서는 브랜드 제품을 맨 앞에 두고 그 안은 유사도 대신 최신순이다. `/code-review`가 "ATOMY …"처럼 이름에 검색어가 없는 제품이 유사도 때문에 뒤로 밀린다고 지적했다. 브랜드 제품을 앞에 두는 것만으로는 "애터미"처럼 걸린 제품이 모두 그 브랜드인 경우를 못 고쳐(107개가 수정 전후 모두 241위 이후), 브랜드 제품끼리는 유사도를 같게 봤다. 브랜드 이름 검색 17개 중 첫 페이지(20개)에 이름 밖 브랜드 제품이 30개 → 81개, 애터미 첫 노출 241위 → 5위. 쿼리 시간은 그대로다(애터미 2.7 → 2.2ms). 유사도는 쓰지 않는다(브랜드 표기가 짧아 오타 허용이 엉뚱한 브랜드를 부른다).
  - 응답 `brand`는 `{id, name}` 객체다. 화면이 배지를 눌러 목록 `brand=` 필터로 넘길 id가 필요하다. 이름은 한 페이지 brandId를 모아 한 번에 조회한다.
